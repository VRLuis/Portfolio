# Internationalization (i18n) Guidelines

## Overview

The portfolio supports multiple languages through a file-based i18n system. Content and UI strings are stored as JSON files organized by language, loaded at build time by Astro pages.

## Current Languages

- **English** (`en`) — Default language
- **Spanish** (`es`)

## Data Structure

The i18n system uses two layers of JSON data:

### 1. UI Translation Keys

Location: `src/data/i18n/[lang].json`

These files contain static UI strings that don't change per section — navigation labels, section titles, button text, and common phrases.

Example structure (`src/data/i18n/en.json`):
```json
{
    "pageTitle": "Luis Villar Roldán | Fullstack Developer",
    "nav": {
        "about": "About me",
        "experience": "Experience",
        "projects": "Projects"
    },
    "sections": {
        "experienceTitle": "Experience and Formation",
        "projectsTitle": "Projects"
    },
    "buttons": {
        "viewCertificate": "View Certificate",
        "moreInfo": "More info +",
        "close": "Close"
    }
}
```

### 2. Content Data by Domain

Location: `src/data/[lang]/[domain].json`

Each content domain has its own JSON file per language. These contain the actual portfolio content — experience entries, project details, certificates, etc.

Available domains:
| Domain | File | Description |
|---|---|---|
| Experience | `experience.json` | Work history, companies, technologies, milestones |
| Formation | `formation.json` | Education and academic background |
| Projects | `projects.json` | Personal and professional projects |
| Technologies | `technologies.json` | Tech stack and skills |
| Certificates | `certificates.json` | Certifications and courses |
| Learning | `learning.json` | Currently learning topics |
| Contact | `contact.json` | Contact information and social links |

## How It Works

### Language Routing

Pages use Astro's dynamic routing with `[lang].astro` to handle language selection. The language code from the URL determines which JSON files are loaded.

### Data Flow

1. **Page** (`src/pages/[lang].astro`) receives the language code from the URL.
2. **Page** imports the corresponding `i18n/[lang].json` for UI strings.
3. **Page** imports domain-specific data from `src/data/[lang]/[domain].json`.
4. **Page** passes translations and data as props to **Sections**.
5. **Sections** pass translations down to **Organisms** and **Molecules**.
6. **Components** use translation keys instead of hardcoded text.

### Example Data Flow

```
Page ([lang].astro)
  ├── imports i18n/[lang].json → { translations }
  ├── imports data/[lang]/experience.json → { experienceData }
  └── renders <Experience translations={translations} experienceData={experienceData} />
       └── Experience.astro passes translations to ExperienceList
            └── ExperienceList passes translations to ExperienceCard
                 └── ExperienceCard uses translations.buttons.viewCertificate
```

## Adding a New Language

1. Create a new language folder: `src/data/[newLang]/`
2. Copy all domain JSON files from an existing language as a template.
3. Translate the content in each file.
4. Create `src/data/i18n/[newLang].json` with translated UI strings.
5. Ensure the `[lang].astro` page route handles the new language code.

## Rules

- **Never hardcode user-facing text** in components. Always use translation keys passed as props.
- **Keep key names consistent** across all language files. If a key exists in `en`, it must exist in `es`.
- **Content data mirrors structure** — `experience.json` in `en/` and `es/` must have the same array length and object keys.
- **UI strings go in `i18n/`** — buttons, labels, titles, navigation text.
- **Domain content goes in `[lang]/`** — experience entries, project descriptions, etc.
- **When adding a new translation key**, add it to all existing language files simultaneously.
